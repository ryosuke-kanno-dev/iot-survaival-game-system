# 設計上の重要な決定事項 (Architecture & Decisions)

SPEC-IR システムを継続的に開発・保守するための、過去の決定事項と設計原則をまとめました。
機能追加やバグ修正の際、これらの思想に反する実装を行わないように注意してください。

---

## 1. 採用した設計と理由

### サーバー権威モデル (Server-Authoritative)
- **概要**: ダメージの適用可否や現在の合計HP、DOWN状態の最終決定権はすべてサーバー側のDB(`apply_damage.php`)が持つ。
- **理由**: チート防止や、複数プレイヤー間の状態の不整合（一方が倒したつもりが相手は生きているなど）を完全に防ぐため。ローカルで計算したHPはあくまで表示用（予測値）として扱う。

### ポーリング方式 (Long Polling / 定期 Fetch)
- **概要**: 2秒に1回、クライアントから `get_match.php` と `get_players.php` を叩いて全体の最新状態を同期する。
- **理由**: 野外でのサバイバルゲーム利用を想定しているため。モバイル回線の切断やスマートフォンのスリープからの復帰時に、一発のAPIリクエストで瞬時に最新状態へ復元できる堅牢さ（ステートレス性）を優先した。

### `version` カラムを用いた差分判定
- **概要**: DBへのUPDATE時に必ず `version` (INT) をインクリメントし、クライアントは前回取得時の `version` と比較して変更があった場合のみイベントを再発火させる。
- **理由**: ポーリングによる無駄なDOM更新（フリッカー現象やパフォーマンス低下）を防ぎつつ、「誰かが1ダメージでも受けたか」を確実かつ低コストで検知するため。

### ダメージキューイングと自動リトライ
- **概要**: 通信失敗時にリクエストをメモリ内キュー(最大10件)に退避し、3秒後・5秒後に自動再送(`sendDamageWithRetry`)する。
- **理由**: 山間部などネットワークが不安定な野外レイテンシを考慮し、一時的な切断によるダメージデータのロストを防ぐため。ブラウザストレージ(localStorage等)は利用せず、一時的なメモリ実装に留めて複雑化を避けている。

## 2. 却下した設計と理由

### WebSocket の利用
- **理由**: リアルタイム性は高いが、コネクションが切断された際の再接続ロジックや状態の再同期（どこまでイベントを取りこぼしたか）の管理が複雑になりすぎるため。ステートフルな接続は野外モバイル環境に不向きと判断した。

### クライアント側（JS）での決定的なDOWN判定
- **理由**: 「HPがゼロになったらJSからDOWN APIを叩く」設計にすると、ネットワーク遅延でAPI呼び出しが遅れた隙に別の処理が走る競合(Race Condition)が発生する。そのため、判定はクライアント(`down-checker.js`)で行うが、それはあくまで表示用であり、最終的なダウン状態の移行はサーバーAPIからの戻り値(`is_down: true`)に従う設計とした。

## 3. やってはいけないこと（Anti-Patterns）

機能改修時に**絶対に避けるべき実装パターン**です。

* **`blur` イベントでセレクトボックス等の値を強制的に戻す処理をつくる**
  * モバイル端末でフォーカスが外れた際の挙動が不安定になり、Admin画面等で無限ループや操作不能バグを引き起こす原因になります。
* **ポーリング処理によってユーザーのUI入力状態を無条件で上書きする**
  * Admin画面のセレクトボックスなど、ユーザーが操作中の要素を2秒ごとの `fetch` で無差別にDBの現在値で上書きすると、「設定を変更しようとした瞬間に初期値に戻る」バグを引き起こします。必ず「サーバーの値が前回から変化した場合のみ更新する」という保護を入れること。
* **UIと内部状態の同期パスをスキップする**
  * `server-sync.js` で取得したデータを、UIモジュール (`ui-health.js` 等) に直接渡して画面だけ更新するのは厳禁です。必ず状態管理モジュール (`health-manager.js`) の `syncFromServer` 等を経由し、そこからのイベントでUIを更新させてください。これを怠ると、内部の合計HPと表示が乖離するバグに繋がります。
* **`server-sync.js`（ポーリング）に依存せず、各UIコンポーネントで直接 `fetch()` や `apiRequest()` を多用する**
  * 状態の二重管理や、ローカル`version`とDBの不整合を引き起こします。データ取得は原則 `serverSync` モジュールに集約させ、イベントディスパッチ(`matchStatusChanged`, `playersDataChanged`) 経由で受け取ってください。
* **初期化関数（`init()`等）の中で `startPolling()` を無条件に呼ぶ**
  * 画面遷移や再描画のタイミングでポーリングタイマーが重複して起動（二重起動）し、サーバーに過剰な負荷をかけ、イベントが2回ずつ発火するバグの温床になります。
* **サーバーと連携せずに `gameState.down()` を単独で呼ぶ**
  * ローカルの画面だけがDOWNし、他のプレイヤーからはPLAYINGに見える「ゴースト状態」を引き起こします。
* **試合終了設定(`END`)のまま強制的に別ステートへ上書き遷移する**
  * `END` 状態から `DOWN` 状態など、許可されていない遷移を `server-sync` 等から強制的に呼び出すとシステムがクラッシュします（`PLAYING` 状態のときのみ `DOWN` を強制するようなガードが必要です）。

## 4. ハマりやすいポイント（Troubleshooting）

* **大文字小文字の不一致 (Case Sensitivity)**
  * DBの `player_state` や `status` は大文字 (`PLAYING`, `DOWN`, `FINISHED`, `WAITING`) で統一されています。JS側で `"playing" === status` のような小文字比較を行うと遷移バグが発生するので注意してください。
* **`apply_damage.php` における `damage_request_id` の重複チェック漏れ**
  * キューイングによる自動リトライ機能があるため、同じダメージリクエストが複数回サーバーに到達する前提で組まれています。API側の重複保護機構(トランザクション + `damage_requests` テーブルチェック)を外すと、1発の被弾で2倍のダメージが入る致命的なバグになります。
* **タイマーのズレと補正（`SERVER_SYNC_CONFIG.TIMER_CORRECTION_THRESHOLD_SEC`）**
  * クライアントは `setInterval` で毎秒カウントダウンしますが、スマホの処理落ち等でズレます。`server-sync.js` が0.5秒以上のズレを検知したときだけ補正をかける仕様です。この閾値を小さくしすぎると、毎秒強制同期がかかり表示がピクつく原因になります。
* **Safari / iOS キャッシュ問題**
  * iOSのブラウザでは `fetch` APIが強力にキャッシュされることがあります。`common.php` 側でCache-Controlヘッダーを出力していますが、独自にエンドポイントを増やす場合はGETリクエストのキャッシュ対策に気をつけてください。
